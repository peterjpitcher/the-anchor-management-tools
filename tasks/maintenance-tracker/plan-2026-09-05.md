# Maintenance and improvements tracker, discovery and plan

Date: 2026-09-05
Status: plan only, no code written, nothing applied
Owner decisions outstanding: see section 12

---

## 1. What you asked for

A place to log two kinds of thing about the pub, and keep them from being forgotten:

- **Issues**: something is broken and needs repairing.
- **Improvements**: something we want to do to the pub that is not a repair, needs budgeting and needs planning in with a contractor.

Both need: who owns it (us or Greene King), an estimated cost when it is ours, date-stamped notes as an audit trail, date-stamped photos, a target date, urgency, area, contractor and status.

Explicit constraint from you: do not make this super complicated. It has to keep us organised, not become a project management system.

---

## 2. Discovery: what already exists

I checked the live database and the codebase. Findings that shape the design:

**Nothing to build on, and nothing to collide with.** There is no maintenance, issue, defect, repair, snag, asset or equipment table anywhere in the 661 migrations. The only near-miss is `phone_standardization_issues`, which is unrelated. This is a clean build.

**The audit-trail pattern already exists and is good.** `public.recruitment_candidate_notes` (`supabase/migrations/20260717000000_recruitment_candidate_notes.sql`) is an append-only, timestamped, attributed notes table with deliberately no UPDATE or DELETE policy, so notes are immutable at the database layer. It snapshots `created_by_email` alongside the `created_by` foreign key so the trail survives a user being deleted. `getRecruitmentCandidateTrail()` in `src/services/recruitment.ts:535` then merges those manual notes with the field-level changes recorded in `audit_logs` into one timeline. That is exactly the audit log you described, and it is already proven in production. Copy it.

**The photo problem is already solved.** `src/lib/expenses/imageProcessor.ts` does magic-byte file type validation, converts HEIC and HEIF to JPEG, rotates by EXIF orientation, strips metadata, resizes the longest edge to 2000px, compresses, and rejects anything over 50 megapixels as a decompression bomb. `sharp` is already a dependency. This matters more than it sounds: iPhones shoot HEIC, browsers cannot display HEIC in an `<img>` tag, and photos straight off a phone are 3 to 5MB. Without this the feature would appear to work and then show broken images. It is reusable as-is.

**Upload size is not a blocker.** `next.config.mjs:110` sets `serverActions.bodySizeLimit: '20mb'`, so a phone photo can go through a server action in one step. The alternative signed-upload-URL pattern (used by receipts and event image variants) exists but is not needed here.

**Storage pattern is settled.** `expense-receipts` (`supabase/migrations/20260405130000_mileage_expenses_mgd.sql:360`) is the model: private bucket, explicit `file_size_limit` and `allowed_mime_types`, storage RLS policies gated on `public.user_has_permission(...)` rather than `is_super_admin` (that hardening happened in `20260708000031_expenses_permission_rls.sql`). Files are stored under a `crypto.randomUUID()` name, never the original filename, with the original kept only in a database column. Display is via `createSignedUrl(path, 3600)`. Metadata insert failure removes the uploaded object.

**Mobile camera capture is new ground.** `capture="environment"` appears nowhere in the codebase. You will be logging most of these while walking round the pub with your phone, so this matters.

**The design system has a `FileUpload` primitive with zero call sites.** Every existing feature rolls its own picker. It works, but it has never run in production, so treat it as unproven.

**Nav count pills are cheap if done right.** `src/actions/get-outstanding-counts.ts` computes nine counts in one `Promise.all` wrapped in `unstable_cache`. Adding a tenth to that existing batch costs almost nothing. Adding a separate query would not: uncached nav counts were previously the single biggest database consumer in this app.

**Live role reality.** Only three roles have any users at all: `super_admin` (4 users), `foh_staff` (1) and `portal_shift_manager` (1). `manager` and `staff` exist but have zero users. So do not over-invest in a permissions matrix; grant sensibly for the future but expect super_admin to be who actually uses this.

**Real area names in the database today.** `table_areas` holds only "Main Bar" and "Dining Room". `venue_spaces` holds "The Dining Room", "Outdoor Terrace/Garden", "The Main Area" and "Entire Pub". Neither list covers cellar, toilets, kitchen or car park, so maintenance needs its own area list.

**Greene King.** The Anchor is operated as a Greene King tenanted pub (recorded in `tasks/lessons.md`, 2026-09-05). Under a tenancy the landlord typically carries building fabric, structure and exterior, and the tenant carries internal repairs, fixtures and fittings. That split is often disputed, and at the moment you spot something you frequently will not know which side it falls on. The design must allow "not yet established" rather than forcing a guess.

## 3. Shape of the solution

One feature, one module, one table for the items, two child tables for notes and photos, plus a small lookup table for areas.

Issues and improvements go in the **same table** with a `kind` discriminator. They share almost every field you listed (area, notes, photos, owner, cost, target date, status, contractor). Splitting them into two tables would mean duplicating the notes table and the photos table and the upload code twice, for the sake of one column. One table with a filter is simpler to build and simpler to use.

## 4. Data model

### 4.1 `public.maintenance_areas`

A small editable lookup so the area is a pick list, not free text that ends up with "carpark", "car park" and "Car Park" as three different things.

| Column | Type | Notes |
|---|---|---|
| `id` | uuid pk | |
| `name` | text, unique, not null | |
| `sort_order` | int, default 0 | |
| `active` | boolean, default true | soft delete, never hard delete an area an item points at |
| `created_at`, `updated_at` | timestamptz | |

Proposed seed (editable in settings afterwards):
Main Bar, Dining Room, Kitchen, Cellar, Toilets (Ladies), Toilets (Gents), Toilets (Accessible), Beer Garden and Terrace, Car Park, Exterior and Building, Function Room, Staff Areas, Plant and Utilities, Signage, Other.

### 4.2 `public.maintenance_items`

| Column | Type | Notes |
|---|---|---|
| `id` | uuid pk | |
| `reference` | text, unique, not null | `M-0001`, auto-generated from a sequence. Gives you something to quote to a contractor or to Greene King. |
| `kind` | text, not null | `issue` or `improvement` |
| `title` | text, not null | short summary, 1 to 200 chars |
| `description` | text, nullable | the detail |
| `area_id` | uuid, not null, FK | |
| `status` | text, not null, default `reported` | see 4.3 |
| `priority` | text, not null, default `medium` | `critical`, `high`, `medium`, `low` |
| `responsibility` | text, not null, default `to_confirm` | `us`, `greene_king`, `to_confirm` |
| `reported_on` | date, not null | when it was **spotted**, not when it was typed in. Defaults to today in London, editable, so logging something three days late still dates correctly. |
| `target_date` | date, nullable | target fix or completion date |
| `completed_on` | date, nullable | |
| `estimated_cost` | numeric(10,2), nullable | |
| `actual_cost` | numeric(10,2), nullable | one extra column, and it is the only way to ever answer "are our estimates any good" |
| `contractor_name` | text, nullable | |
| `contractor_contact` | text, nullable | phone or email, so you are not digging through your phone for it |
| `created_by`, `created_by_email` | uuid, text | email snapshotted, per the recruitment pattern |
| `created_at`, `updated_at` | timestamptz | |

Database constraints worth enforcing:

- `status = 'done'` requires `completed_on` to be set. Stops the "marked done, no idea when" mess.
- `estimated_cost` and `actual_cost` must be `>= 0` when set.
- `target_date >= reported_on` when both are set.

Deliberately **not** enforced: costs are allowed on a Greene King item too. You will sometimes want to record what a job is worth even when you are arguing that they should pay for it. The form will only prompt for cost when responsibility is "us", which is the behaviour you asked for, but the database will not block it.

Two implementation notes that are easy to get wrong:

- The `reported_on` default must be `(timezone('Europe/London', now()))::date`, not `current_date`. The database runs in UTC, so between midnight and 1am British Summer Time a plain `current_date` returns yesterday. Date handling is the single most repeated bug class in this codebase (63 fixes across six repos), so this is worth being explicit about.
- The reference sequence needs `GRANT USAGE ON SEQUENCE ... TO authenticated`, or inserts fail with a permission error that does not obviously point at the sequence.

### 4.3 Status lifecycle

One list covering both kinds:

| Status | Meaning |
|---|---|
| `reported` | logged, nothing done yet |
| `quoting` | getting prices, waiting on a quote |
| `awaiting_landlord` | reported to Greene King, waiting on them. Shown in the UI as "With Greene King" |
| `scheduled` | contractor booked, date in the diary |
| `in_progress` | work underway |
| `on_hold` | parked deliberately, for budget or season |
| `done` | completed |
| `cancelled` | decided against |

`awaiting_landlord` is the one that earns its place. "Reported to Greene King six weeks ago and heard nothing" is precisely the thing that gets forgotten, and it is a different question from "who pays", which is what `responsibility` answers.

The database column is named `awaiting_landlord` rather than `greene_king` so the tenancy changing does not mean a data migration.

If you want this shorter, `quoting` and `in_progress` are the two safest to drop.

### 4.4 `public.maintenance_notes`

Direct copy of `recruitment_candidate_notes`: `id`, `item_id` (cascade delete), `content`, `kind` (`note`), `created_by`, `created_by_email`, `created_at`. Index on `(item_id, created_at DESC)`. RLS with SELECT and INSERT policies only, and **no UPDATE or DELETE policy**, so the trail is immutable at the database layer. That is what makes it a real audit log rather than an editable comment box.

### 4.5 `public.maintenance_photos`

`id`, `item_id` (cascade delete), `storage_path`, `file_name`, `mime_type`, `file_size_bytes`, `caption` (nullable), `taken_on` (date, nullable, for when the photo predates the upload), `uploaded_by`, `uploaded_by_email`, `uploaded_at`. Index on `(item_id, uploaded_at DESC)`.

Photos attach to the item, not to individual notes. Each carries its own timestamp and uploader, which is the date-stamping you asked for, and it avoids a photo becoming orphaned when you would rather it sat against the item as a whole.

### 4.6 Storage bucket

`maintenance-photos`, **private**, `file_size_limit` 20MB, `allowed_mime_types` jpeg, png, webp, heic, heif. Storage RLS policies gated on `public.user_has_permission(auth.uid(), 'maintenance', ...)`, following `20260708000031_expenses_permission_rls.sql` rather than the older `is_super_admin` form.

## 5. The audit trail

`getMaintenanceItemTrail(itemId)` merges three sources into one reverse-chronological timeline, exactly as `getRecruitmentCandidateTrail` does:

1. Your typed notes from `maintenance_notes`.
2. Field-level changes from `audit_logs` where `resource_type = 'maintenance_item'` and `resource_id` matches. Every status change, cost change, contractor change and date change lands here automatically because every server action already writes an audit event.
3. Photo uploads.

The practical effect: you type a note when you have something to say, and the system records everything else on its own. "Status changed from Reported to With Greene King on 12 September by Peter" appears without anyone typing it.

Following the recruitment precedent, the UI shows your notes as the primary list and puts the automatic system events behind a collapsed toggle, so the trail stays readable.

## 6. Permissions

New module `maintenance` added to `ModuleName` in `src/types/rbac.ts`, with three actions:

| Action | Who | What it allows |
|---|---|---|
| `view` | staff, foh_staff, manager, super_admin | see the list and detail |
| `report` | staff, foh_staff, manager, super_admin | create an item, add notes, add photos |
| `manage` | manager, super_admin | edit status, costs, contractor, dates, responsibility; delete |

Splitting `report` from `manage` is what lets a bartender log a broken toilet without being able to change the money. Given only super_admin and foh_staff have real users today, this costs nothing now and is correct later.

Migration follows the vouchers pattern (`supabase/migrations/20260802000001_voucher_foundation.sql:218`): insert into `public.permissions` with `on conflict (module_name, action) do nothing`, then `cross join public.roles` filtered by name into `role_permissions`.

## 7. Screens

Mobile-first throughout. You will log most of these on your phone while walking round, and review them at a desk.

**`/maintenance`, the list.** Summary strip across the top: open items, overdue, estimated spend outstanding. Filters for kind, status, area, responsibility, priority, and an "overdue only" toggle. Search on title and reference. Cards on mobile, table on desktop. A prominent "Log an issue" button.

**`/maintenance/new`.** A full page rather than a modal, because a modal on a phone with a camera picker in it is where this sort of thing usually falls over. Minimum to save: kind, title, area, priority. Everything else optional, so logging something takes fifteen seconds. Photo capture available directly on this form.

**`/maintenance/[id]`, the detail.** Header with reference, title and status badges. A fields panel that is editable in place for anyone with `manage`. The photo grid. The timeline (notes plus system events). An always-visible "Add a note" box at the top of the timeline, because if adding a note takes two clicks it will not happen.

**`/settings/maintenance`.** Manage the area list. Sits alongside the existing `settings/categories`, `settings/pay-bands` and `settings/customer-labels` pages.

### Photo capture specifics

The file input needs `accept="image/jpeg,image/png,image/webp,image/heic,image/heif"` and `capture="environment"`, which makes a phone open the rear camera directly instead of the file browser. Choosing a file uploads it immediately with no second step, following the note in `SquareImageUpload.tsx:42` recording that a previous two-step flow silently discarded the chosen file when the form was closed.

The upload goes through a server action as `FormData`, is validated by magic bytes rather than trusting the declared type, runs through `optimiseImage()` (HEIC becomes JPEG, EXIF rotation applied, resized to 2000px), is stored under a random UUID filename, and is displayed via a one-hour signed URL. If the metadata insert fails, the uploaded object is removed. If the upload fails, **the user sees the failure**, per the workspace rule that write paths fail closed rather than silently.

## 8. Stopping things being forgotten

This is the actual point of the feature, so it gets two mechanisms.

**Nav count pill (phase 1).** A badge on the Maintenance nav item counting items that are overdue or due within seven days, excluding done and cancelled. You see it every time you use the app for anything else. It must be added to the existing `computeOutstandingCounts()` `Promise.all` in `src/actions/get-outstanding-counts.ts`, inside the existing `unstable_cache`, and to the `countById` map in `src/ds/shell/SidebarNav.tsx`. Adding a separate query instead would reintroduce the nav-count cost problem that was fixed previously.

**Weekly digest email (phase 2).** Monday 09:00 London, copying `src/app/api/cron/checklists-weekly-summary/route.ts` (hourly Monday cron gated on the London hour, so British Summer Time cannot skip it). Four sections: overdue, due in the next fourteen days, sitting with Greene King for more than twenty-one days, and reported over thirty days ago with no activity. That last one is the "quietly forgotten" list.

## 9. Build order and deployment sequence

The ordering here is not cosmetic. Two previous incidents in this repo came from getting it wrong: code that reads a new column deployed before its migration broke production, and an RBAC grant applied before its code deploy put a sidebar item in front of a route that did not exist.

**Step 0.** Move `src/lib/expenses/imageProcessor.ts` to `src/lib/images/imageProcessor.ts` with a re-export shim at the old path, so both expenses and maintenance import it from a neutral home. Roughly ten minutes, and it avoids maintenance importing from the expenses domain.

**Step 1, migration A (schema).** `maintenance_areas` with seed data, `maintenance_items` with its sequence and constraints, `maintenance_notes`, `maintenance_photos`, the `maintenance-photos` storage bucket, all RLS policies, and the sequence grant. Apply this **before** the code deploy. Then run `npx tsx scripts/security/assert-anon-surface.ts`, which is mandatory after any migration adding a table (four new tables here), and confirm nothing new is exposed to anon.

**Step 2, the code.** Types, service layer (`src/services/maintenance.ts`), server actions (`src/app/actions/maintenance.ts`), the four pages, the nav entry, the count wiring. Build, lint, typecheck, test, deploy, and verify the deployment actually landed in production rather than assuming a green check means live.

**Step 3, migration B (permissions).** The `permissions` and `role_permissions` inserts. Apply this **after** the code is live, so the nav item never points at a missing route.

**Step 4, phase 2.** Weekly digest cron plus its `vercel.json` entry.

Everything goes through the `prod-migrate` skill, and applying to production needs your explicit go-ahead each time.

## 10. Testing

Vitest, and the suite must pass under both `npm test` (pinned to Europe/London) and `npm run test:utc`:

- Overdue calculation across a British Summer Time boundary, and the `reported_on` default at 00:30 London in summer.
- The `status = 'done'` requires `completed_on` constraint.
- Photo upload with a HEIC fixture, asserting a JPEG comes out.
- Photo upload with a failing storage dependency, asserting the user sees an error and no orphan row is left behind.
- Notes are append-only: attempting an update or delete as an authenticated user is refused.
- Any checkbox posted through `FormData` uses `src/lib/forms/formBoolean.ts`, never `z.coerce.boolean()`, because `Boolean("false")` is `true`.

## 11. Deliberately out of scope

Listed so it is a decision rather than an oversight:

- Recurring or planned preventative maintenance schedules (gas safety, PAT testing, extraction cleaning). Real, but a different feature.
- Asset register, warranties, serial numbers.
- Contractor database. `contractor_name` is free text for now. There are already two vendor tables (`vendors` for private-booking suppliers, `invoice_vendors` for billing) and picking one, or adding a third, is a decision worth making separately once you see which contractors actually recur.
- Linking an item to a receipt to prove actual spend. Attractive, and `receipt_transactions` exists, but it doubles the surface area for little day-one benefit.
- Putting scheduled contractor visits on the Pub Ops Google Calendar. Genuinely useful, deferrable to phase 2.
- Any public or customer-facing surface. This is staff-only.
