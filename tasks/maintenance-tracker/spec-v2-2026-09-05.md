## 0. What changed from v1, and why

v1 made three claims that empirical testing has now disproved. They are corrected here.

| v1 claim | Verdict | What is actually true |
|---|---|---|
| "Upload size is not a blocker, `bodySizeLimit: '20mb'` means a phone photo goes through a server action in one step" | **Wrong** | Vercel rejects any request body over roughly 4.49MB at the proxy, before the function runs. Probed live against `management.orangejelly.co.uk`: 4,492,000 bytes accepted, 4,494,000 bytes returns `413 FUNCTION_PAYLOAD_TOO_LARGE`. `bodySizeLimit` only raises the Next.js framework cap; it cannot raise the platform cap. |
| "The photo problem is already solved, `imageProcessor.ts` converts HEIC to JPEG" | **Wrong** | sharp's prebuilt binaries bundle libheif without the libde265 HEVC decoder. A real iPhone HEIC throws `heif: Error while loading plugin: Support for this compression format has not been built in`. Reproduced by running the actual function against genuine HEVC-coded HEIC files. `sharp.format.heif.input === true` covers AVIF only, not HEIC. The existing tests mock sharp entirely and pass a 200-byte buffer, so they could never have caught this. |
| "This is a clean build, nothing to collide with" | **Overstated** | No dedicated maintenance table exists, that part holds. But `public.table_holds` already carries a live `hold_type = 'maintenance'`, switched **on** in production. A second, unrelated meaning of "maintenance" now exists in the app and the two must be kept visibly distinct. |

Two further findings change the plan's shape:

- **The three-step deploy sequence in v1 was not a gate.** Production `user_has_permission` returns `true` for a super-admin on any module and action pair, including invented ones (tested with `totally_made_up` / `frobnicate`). Deferring a permissions migration therefore does not keep the feature switched off.
- **The Friday managers email exists.** The review could not find it because its checkout was 12 commits behind. It was merged today as PR #123 (`codex/friday-manager-report`) and is a designed extension point. Details in section 7.

Everything the owner decided in the review stands unchanged and is not re-opened.

## 1. Scope

Track two kinds of thing about the pub and stop them being forgotten:

- **Issue**: something is broken and needs repairing.
- **Improvement**: something we want to do that is not a repair, needs budgeting and planning with a contractor.

Both carry: responsibility (us or Greene King), estimated cost, date-stamped notes forming an audit trail, date-stamped photos, target date, urgency, area, contractor and status.

**Explicitly out of scope**: contractor database, assignment engine, approval workflow, asset register, recurring or preventative maintenance schedules, receipt reconciliation, calendar integration, booking availability automation, emergency alerting, offline sync, and any customer-facing surface.

**Not implied by this tracker**: logging a critical item does not alert anyone immediately, does not block bookings and does not establish who is contractually liable.

---

## 2. Access, settled

**Super-admins only, for every interactive action**: viewing, creating, editing, notes, photos, history, costs and area administration. Manager, staff, FOH and portal roles get nothing.

**Enforcement primitive.** Do not add a `maintenance` ModuleName or a `report` ActionType, and do not route this through `checkUserPermission`. That function returns true for super-admins regardless of whether permission rows exist, so it cannot express "super-admin only" as a restriction, only as a floor. Use an explicit super-admin check, matching how existing super-admin-only features (expenses) do it: `public.is_super_admin(auth.uid())` in RLS, and the equivalent server-side check in pages and actions.

Consequence: **there is no permissions migration**, and the release has two steps, not three.

Enforcement must be applied at every layer independently: page, server action, RLS policy, storage policy, signed-URL issuance, nav count payload, and the timeline reader. Hiding a nav item is not a boundary.

## 3. Data model

### 3.1 `public.maintenance_areas`

| Column | Type | Notes |
|---|---|---|
| `id` | uuid pk | |
| `name` | text not null | unique on a normalised form: trimmed, collapsed whitespace, case-insensitive |
| `sort_order` | int not null default 0 | |
| `active` | boolean not null default true | soft delete only |
| `created_at`, `updated_at` | timestamptz not null default now() | |

Seed, approved (fifteen): Main Bar, Dining Room, Kitchen, Cellar, Toilets (Ladies), Toilets (Gents), Toilets (Accessible), Beer Garden and Terrace, Car Park, Exterior and Building, Function Room, Staff Areas, Plant and Utilities, Signage, Other.

Lifecycle rules: an inactive area stays visible and filterable on existing items but cannot be chosen for new ones. If an area is deactivated while a form is open, the save fails with a clear message rather than silently reassigning. Items show the area's current name; renames are not snapshotted, and the rename itself is recorded in history.

### 3.2 `public.maintenance_items`

| Column | Type | Notes |
|---|---|---|
| `id` | uuid pk default gen_random_uuid() | immutable |
| `reference` | text not null unique | `M-0001`, from a sequence; immutable |
| `kind` | text not null | CHECK in (`issue`, `improvement`) |
| `title` | text not null | CHECK length(btrim(title)) between 1 and 200 |
| `description` | text | CHECK length <= 5000 when present |

| `responsibility` | text not null default `to_confirm` | CHECK in (`us`,`greene_king`,`to_confirm`) |
| `reported_on` | date not null default `(timezone('Europe/London', now()))::date` | when it was spotted. **Owner decision, 2026-09-06: editable after logging**, so something noticed weeks ago is dated truthfully rather than dated today. `target_date` is validated against it on both client and server. |
| `target_date` | date | |
| `completed_on` | date | |
| `estimated_cost` | numeric(10,2) | CHECK >= 0 |
| `actual_cost` | numeric(10,2) | CHECK >= 0 |
| `contractor_name` | text | CHECK length <= 200 |
| `contractor_contact` | text | CHECK length <= 200 |
| `created_by` | uuid references auth.users(id) ON DELETE SET NULL | immutable after insert |
| `created_by_email` | text | server-derived snapshot, never client-supplied |
| `created_at` | timestamptz not null default now() | |
| `updated_at` | timestamptz not null default now() | maintained by trigger, not by the app |

Constraints:

- `status = 'done'` requires `completed_on IS NOT NULL`; every other status requires it to be NULL.
- `target_date >= reported_on` when both are set.
- Blank strings normalise to NULL on write.
- Future `reported_on` and future `completed_on` are rejected (dates are in London).

Notes on two things that are easy to get wrong:

- The `reported_on` default must use `timezone('Europe/London', now())`. The database runs in UTC, so a plain `current_date` returns yesterday between midnight and 01:00 British Summer Time.
- The reference sequence needs `GRANT USAGE ON SEQUENCE ... TO authenticated`, or inserts fail with a permission error that does not name the sequence. Format beyond 9,999 by widening naturally (`M-10000`), never by truncating. Gaps are expected and acceptable.

### 3.3 Statuses, all eight

`reported`, `quoting`, `awaiting_landlord` (displayed "With Greene King"), `scheduled`, `in_progress`, `on_hold`, `done`, `cancelled`.

Column value is `awaiting_landlord`, not `greene_king`, so a change of tenancy is not a data migration. It answers "what is happening now", which is a different question from `responsibility`, which answers "who pays".

**Open** = any status other than `done` and `cancelled`. This single definition drives the email, the totals and the nav count.

Lifecycle:
- Moving to `done` defaults `completed_on` to today in London, editable for late recording.
- Reopening from `done` clears `completed_on` and keeps the completion event in history.
- `cancelled` is reversible back to `reported`.
- Closed items (`done`, `cancelled`) still accept notes and photos, because evidence often arrives late.

### 3.4 `public.maintenance_notes`

`id`, `item_id` (FK, ON DELETE RESTRICT), `content` (not null, 1 to 5000 chars), `created_by` (ON DELETE SET NULL), `created_by_email`, `created_at`.
Index on `(item_id, created_at DESC)`.
RLS: SELECT and INSERT only, both gated on `is_super_admin`. **No UPDATE or DELETE policy.**

Note the FK is `RESTRICT`, not `CASCADE`. v1 said cascade, which would let deleting an item silently erase its own audit trail.

### 3.5 `public.maintenance_photos`

`id`, `item_id` (FK, ON DELETE RESTRICT), `storage_path` (not null, unique), `file_name`, `mime_type`, `file_size_bytes` (CHECK > 0), `width`, `height`, `caption`, `taken_on` (date), `uploaded_by` (ON DELETE SET NULL), `uploaded_by_email`, `uploaded_at`, `state` (CHECK in `pending`, `ready`, `failed`).

The `state` column is what makes upload recovery possible: a row is created `pending` when the upload URL is issued and promoted to `ready` only after the server verifies the stored object. Only `ready` rows are ever read or displayed.

### 3.6 `public.maintenance_item_history`

This is the change I most want the developer to notice.

v1 claimed field-level history came free from `audit_logs`. It does not. `logAuditEvent` writes a separate row through the service-role client after the mutation has already committed, logs any insert error to the console and swallows it, and returns nothing. A caller cannot tell whether the event was written, and a failed write cannot roll back the change. `getRecruitmentCandidateTrail` also returns changed key names from `new_values`, not before-and-after values.

So for guaranteed history, use a database trigger:

`id`, `item_id` (FK RESTRICT), `changed_at` timestamptz not null default now(), `changed_by` uuid, `changed_by_email` text, `field` text not null, `old_value` text, `new_value` text.

An `AFTER INSERT OR UPDATE` trigger on `maintenance_items` writes one row per changed field, in the same transaction as the change. If the history write fails, the change fails. That is what "guaranteed audit trail" actually requires.

Actor attribution comes from `auth.uid()` inside the trigger, with the email resolved server-side. Writes made by the service role record a system actor rather than a null.

Continue calling `logAuditEvent` as well, for consistency with the rest of the app, but never rely on it for the item's own history.

### 3.7 Storage

Bucket `maintenance-photos`, **private**, `file_size_limit` 10485760 (10MB, comfortably above a client-downscaled photo), `allowed_mime_types` `image/jpeg, image/png, image/webp`. **HEIC is deliberately excluded**, see section 4.

Storage RLS on `storage.objects` gated on `is_super_admin(auth.uid())` for SELECT, INSERT and DELETE, scoped to `bucket_id = 'maintenance-photos'`.

Path shape: `{item_id}/{uuid}.{ext}`. Never the original filename.

## 4. Photos: the corrected design

This section replaces v1 entirely. Both of v1's technical premises were false.

**Constraint 1.** Vercel rejects request bodies over about 4.49MB at the proxy, before the function runs. Server-side compression can never help, because the code never executes. Verified live.

**Constraint 2.** Server-side HEIC decoding does not work on the production runtime and cannot be made to work without shipping a different native codec. Verified by execution.

**Constraint 3.** Client-side HEIC transcoding by iOS cannot be relied upon. WebKit's accept-attribute HEIC logic is `#if PLATFORM(MAC)`; the iOS JPEG conversion comes from PHPicker "Compatible" mode, which is not keyed to the accept attribute, and Files-app picks deliver raw HEIC regardless.

### The design

1. **Browser-direct upload via a signed upload URL.** Request URL from a server action, `uploadToSignedUrl` from the browser, then confirm with a second server action. This is the proven pattern in this repo: receipts, event image variants, employee attachments and right-to-work documents all use it, and `receipt_files` holds 517 production rows including one of 21.6MB. It bypasses the function request limit entirely, because the bytes never traverse a function.

2. **Client-side normalisation before upload.** Draw the chosen image onto a canvas, scale the longest edge to at most 2000px, and export as JPEG at quality 0.8. This bounds the size, strips EXIF (applying orientation as it draws), and normalises the format. On iOS Safari, which decodes HEIC natively, this converts HEIC to JPEG on the device, which is where the conversion belongs.

3. **If the browser cannot decode the file**, the canvas draw fails. Catch it and show plain English: "That photo could not be read. On an iPhone, try Settings, Camera, Formats, Most Compatible, or choose a different photo." Never surface a raw codec error.

4. **`accept="image/jpeg,image/png,image/webp"`**, deliberately excluding HEIC. This also stops Safari 17+ converting a JPEG into HEIC on the way out.

5. **Two separate controls**, not one: "Take photo" (`capture="environment"`) and "Choose existing photo" (no capture attribute). `capture` is a hint that browsers may ignore, and a single control that only offers the camera makes an older photo impossible to attach.

6. **Server-side verification after upload**, reading the object from private storage: magic-byte type check, decoded dimensions, and size. Only then is the row promoted to `ready`. No HEIC decode is attempted at any point.

7. **Display** uses a plain `<img>` on a signed URL, not `next/image`. `images.remotePatterns` allows only the public storage path, and the production optimiser rejects a `/sign/` path with `400 INVALID_IMAGE_OPTIMIZE_REQUEST`. A plain `<img>` is unaffected and the CSP permits it. Signed URLs are issued for one hour, generated only after a super-admin check on that specific item, regenerated on expiry, and never persisted or placed in the email.

### Save first, then photos

Approved by the owner and unchanged. Saving the item happens first and produces a durable record. Photo capture is offered on the detail page afterwards. A failed photo never discards the item, each photo succeeds or fails independently, and a failure offers retry.

### Upload recovery

Every branch must be defined, not just the happy path:

| Situation | Behaviour |
|---|---|
| Upload URL issued, browser never uploads | `pending` row expires; a cleanup pass removes stale pending rows and any orphaned object after 24 hours |
| Object stored, confirm call fails or is lost | Confirm is idempotent on `storage_path`; retrying promotes the same row rather than creating a second |
| Confirm runs twice | Unique `storage_path` makes the second a no-op |
| Server verification rejects the file | Object deleted, row marked `failed`, user told why |
| Object delete during cleanup fails | Logged for reconciliation with a correlation id; never retried into a loop |
| Permission lost mid-upload | Confirm re-checks super-admin and refuses |

## 5. History and deletion

**Items are cancelled, not deleted.** There is no ordinary delete. Child FKs are `RESTRICT`, so nothing can silently erase a trail.

**Exceptional removal**, for a wrongly uploaded or sensitive photo, is a distinct, attributed action available only to a super-admin: it deletes the stored bytes, keeps the metadata row marked as redacted with who did it and when, and records a history entry. Redaction is never presented as deletion.

**The timeline** merges, newest first:
1. Notes from `maintenance_notes`.
2. Field changes from `maintenance_item_history`, showing old and new values.
3. Photo events.

Notes are the primary list; system events sit behind a collapsed toggle, following the recruitment precedent. A failed history read is shown as an explicit error, never as an empty trail. The timeline is paginated with a "load older" control, not silently capped at a fixed number of rows.

## 6. Costs and totals

Recorded and displayed in **pounds including VAT**. No tax is calculated anywhere.

- **Our open estimate**: sum of non-null `estimated_cost` on open items where `responsibility = 'us'`.
- **Uncosted**: a count of open `responsibility = 'us'` items with a null `estimated_cost`. Null is not zero and must never be summed as zero.
- Greene King and to-confirm amounts are shown separately and never added to our total.
- `on_hold` is open, so it is included; it is labelled.
- `actual_cost` is a recorded amount, not a reconciled payment, and is labelled as such.

List summaries follow the active filters and say so when filtered.

**Overdue** = `target_date < today in London` on an open item. Due today is not overdue. This predicate is defined once and reused by the list, the badge and the email.

## 7. The Friday managers email

The review could not locate this email and flagged it as a P1 unknown. It exists. It was merged today, 2026-09-05, as PR #123 `codex/friday-manager-report`, in commits `8554972c` and `211386d8`, which are on `origin/main` but were not in the reviewed checkout.

What it is:

- Route `src/app/api/cron/manager-weekly-report/route.ts`, library `src/lib/manager-report/` (`delivery.ts`, `queue.ts`, `render.ts`, `schedule.ts`, `types.ts`), documented at `docs/manager-weekly-report.md`.
- Delivery runs hourly on Friday (`0 * * * 5`) and sends from 09:00 Europe/London. Contributing snapshots run at `0 7,8 * * 5`, two UTC slots covering winter and summer, each gating on the local hour being 08.
- Recipient defaults to `MANAGER_EMAIL`, falling back to `manager@the-anchor.pub`.
- Sections are a typed list, `MANAGER_REPORT_SECTIONS` in `types.ts`. Checklists, private bookings, rota, leave and recruitment have already been consolidated into it.
- Items are queued into `email_messages` with `comm_type = 'manager_report_item'` via `queueManagerReportEmail()`. The id is a stable hash of section, key and recipient, upserted with `ignoreDuplicates`, so re-running a producer cannot duplicate an entry.
- Missing snapshots are already labelled "unavailable" by the renderer, and a long report already falls back to an HTML attachment.

**Important status.** It has never run. Production holds zero `manager_report_item` rows, and the first delivery is Friday 11 September 2026. We would be extending a subsystem that is merged but not yet exercised. That argues for adding maintenance as a separate producer that queues into the report, and changing nothing in the report's core beyond adding one section name.

### The maintenance integration

The report is an event queue: producers add updates that happened. "All outstanding items" is a state snapshot. So maintenance follows the snapshot pattern that checklists, private bookings and rota already use.

1. Add `'maintenance'` to `MANAGER_REPORT_SECTIONS`.
2. New route `src/app/api/cron/maintenance-weekly-snapshot/route.ts`: authorise the cron, gate on Friday 08:00 London, query every open item, render, and call `queueManagerReportEmail({ section: 'maintenance', key: <the Friday's ISO date>, to: MANAGER_EMAIL, ... })`.
3. `vercel.json`: `{"path": "/api/cron/maintenance-weekly-snapshot", "schedule": "0 7,8 * * 5"}`.
4. On a read failure, return 500 and queue nothing, so the report labels the section unavailable rather than implying zero outstanding items.

Content: every item whose status is neither `done` nor `cancelled`. Both kinds, all priorities, all responsibility values, undated, on-hold and future-dated included. **No age or inactivity filter.** Each item once. Fetch every page; the list must not be bounded by any UI page size.

Per item: reference, title, area, status, priority, responsibility, target date or "not set", and a link to the detail page. The link requires a super-admin login; sending to the mailbox does not grant its reader app access. Escape all user-entered text. Never put a signed photo URL in the email.

Preserve every existing section. An empty maintenance set must not suppress the email.

## 8. Screens

Mobile-first. Most items get logged on a phone while walking round.

- **`/maintenance`**: summary strip (open, overdue, our open estimate, uncosted count); filters for kind, status, area, responsibility, priority and overdue-only; debounced search on title and reference; cards on mobile, table on desktop; filters preserved on return. Paginated with stable tie-breaking on `(created_at DESC, id DESC)`. **Owner decision, 2026-09-06: the list opens on "Open only" rather than all statuses**, because the tracker exists to surface outstanding work and closed items would bury it. "All statuses" is the adjacent option, not a hidden one.
- **`/maintenance/new`**: a full page, not a modal. Required: kind, title, area, priority. Everything else optional, so logging takes seconds. No photo control here; saving redirects to the detail page.
- **`/maintenance/[id]`**: header with reference, title and badges; editable fields with explicit save and cancel; photo grid with thumbnails and lazy loading; timeline with an always-visible note box.
- **`/settings/maintenance`**: area administration, super-admin only.

### Concurrency and errors

Explicit save and cancel, never ambient auto-save. Optimistic concurrency using `updated_at`: a stale write is refused with a reload-and-reapply prompt rather than silently overwriting. Form input is retained on a failed save. Create and add-note are idempotent on retry. Not-found, denied and temporary failure are distinguishable without revealing whether a record exists.

### Accessibility

Target WCAG 2.2 AA: labelled inputs, keyboard-operable controls including both photo buttons, visible focus, errors associated with their field and focused on failure, upload status announced politely, status conveyed by text not colour alone, meaningful alternative text for photos, sufficient contrast, and 200% zoom reflow. Mobile cards and desktop tables expose the same information. Empty, no-results, loading and error states all designed.

## 10. Testing

- **Fix the timezone gate first.** There is no `test:utc` script, and `vitest.config.ts` hardcodes `env: { TZ: 'Europe/London' }`, which overrides a command-line `TZ`. `TZ=UTC npm test` therefore runs London twice and records a false green. Add a second Vitest config that reads the zone from an env var, add the `test:utc` script, and assert the effective worker timezone inside the suite so the gate cannot silently regress.
- **Append-only must be asserted on data state, not on errors.** An UPDATE or DELETE blocked by RLS affects zero rows and raises nothing. Proved on PostgreSQL 17. A test that expects a thrown error will pass whether or not the policy exists.
- **One real HEIC fixture test with sharp unmocked**, asserting the chosen rejection behaviour. The existing mocked suite would pass regardless of what sharp does, which is precisely how this defect survived.
- Dates: `reported_on` default at 00:30 London in summer, both DST transitions, overdue and due-today boundaries, backdated reporting.
- Trigger history: old and new values, actor, and that a forced history failure rolls back the item change.
- Upload: every row of the recovery table in section 4.
- Access: a super-admin succeeds; anonymous, manager, staff, FOH and portal users are refused on page, action, RLS, storage, signed URL, count and area settings.
- Email: fixtures proving all existing sections survive, that an empty maintenance set does not suppress the email, that a read failure marks the section unavailable, and that re-running the producer does not duplicate.
- Any `FormData` checkbox uses `src/lib/forms/formBoolean.ts`, never `z.coerce.boolean()`.

## 11. Release

**Two steps, not three.** There is no permissions migration, because super-admin access does not depend on permission rows.

Because of the working tree state, isolation is mandatory:

- Local `main` is **12 commits behind** `origin/main`. Rebase onto origin/main first, or the Friday report will be missing.
- The primary working tree has **51 modified files** of unrelated private-bookings work and two unapplied migrations (`20260905180000`, `20260905180100`). `npx supabase db push` applies every pending migration file, so pushing from this tree would ship someone else's in-progress work.
- Build in a dedicated worktree off `origin/main`, on a branch, and confirm the pending migration set immediately before any push.

1. **Migration**: areas with seed, items with sequence and constraints, notes, photos, history table and trigger, storage bucket, all RLS, sequence grant. Apply before the code. Then run `npx tsx scripts/security/assert-anon-surface.ts`, mandatory after adding tables, and confirm nothing is exposed to anon.
2. **Code**: types, service, actions, four pages, nav entry, count wiring, snapshot cron, `vercel.json` entry.
3. Verify the deployed commit and production alias, record the deployment id and migration versions.

Rollback preserves the tables and any entered evidence, disables the feature and its email section, and never drops an evidence-bearing table.

Everything destined for production goes through the `prod-migrate` skill and needs explicit approval each time.

- The maintenance email extends a subsystem that has never run in production. Its first real execution is Friday 11 September 2026, and ours would be the first added section.
